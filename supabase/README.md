# Database and backend (Supabase)

PostgreSQL on Supabase is the system of record. The business rules that must be atomic
(file numbers, the running bill, posting an invoice, claim batches, dispensing, the public
booking inquiry) live in the database as functions, guarded by row-level security and the
permission keys of doc §1.4. The browser talks to Supabase directly with the publishable key;
there is no separate API server in phase 1. Offline sync (PowerSync) and messaging adapters
(WhatsApp, SMS) attach to this same database later.

The full design (entity diagram, tables, state machines, permission matrix, function list) is in
[docs/database-design.md](../docs/database-design.md).

Project: `wwxmdqdrdekpzcbijsqo` · API `https://wwxmdqdrdekpzcbijsqo.supabase.co`.

## Apply to the Supabase project

Pick one of the two routes.

**A. One paste (no password needed).** Open the Supabase dashboard → SQL editor → New query,
paste the content of `supabase/all.sql` (regenerate with `pnpm db:bundle` after any change) and
run it once on the empty project.

**B. From this machine.** Supabase → Project settings → Database → Connection string → _Session
pooler_ (IPv4). Put it in the root `.env` as `SUPABASE_DB_URL=postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres`,
then:

```sh
pnpm db:apply --seed      # migrations once each (tracked in mmc_migrations), then the seed
```

Then, for both routes:

1. Authentication → Sign In / Providers → Email: turn **off** "Confirm email" (staff accounts
   are created by the manager) and keep the minimum password length at 6 (PINs are six digits).
2. `pnpm db:seed-staff` creates the sample staff accounts (usernames and PINs are printed).
3. `pnpm dev`: the public site now reads practitioners, prices, insurers, hours and the live
   "clinic now" status from the database, booking inquiries are stored, and staff sign in through
   Supabase Auth. If the database is unreachable the pages fall back to sample data.

`pnpm db:check` must pass before every push: it executes all migrations and the seed in PGlite
and proves the rules (file numbers, the 85/15 RSSB split, immutability after posting, FEFO
dispensing, the anonymous inquiry limits, the sensitive-data policy, the public read surface).

## How the pieces fit

- **Identity.** Staff sign in with `username` + PIN; the app maps the username to
  `username@staff.muhaziclinic.rw` for Supabase Auth. `profiles` holds role, station and
  dashboard rights and is created by the `handle_new_user` trigger from the user metadata.
  PIN login on a shared device (doc §5.12) means: one Auth session per device user, a short PIN
  as the Auth password, auto-lock in the app after five minutes.
- **Permissions.** `role_permissions` maps each role to keys such as `patient.write`,
  `clinical.read`, `charge.manual`, `sensitive.read`. Every table has RLS policies that call
  `has_perm()`. Managers read everything except `hiv_test`; receptionists never reach clinical
  tables; cashiers never reach notes.
- **Public site.** The `anon` role can read `public_practitioners`, `public_booked_slots` (busy
  slots only, no names), `public_service_lines`, `public_payers`, call `public_clinic_info()`,
  `public_clinic_status()` and `create_appointment_inquiry()`, which validates the phone, checks
  working hours and free slots, holds the slot for 24 hours and returns `MMC-2026-0001`.
  Everything else is refused.
- **Calendars.** `practitioner.working_hours` is `{"1":[["08:00","17:00"]], …}` keyed by JS
  weekday; the booking page builds the grid from it and from `public_booked_slots`, and the
  database re-checks both when the inquiry is created, so two people cannot take one slot.
- **The running bill.** Opening an encounter creates a draft invoice. Every station calls
  `add_charge()`; the price comes from the payer's price list (fallback to cash with a flag) or is
  typed with a reason when the service allows it. Lines store office, performer, price origin and
  the frozen coverage percentage. `post_invoice()` assigns `INV-<year>-<seq>`, freezes the invoice
  (triggers refuse later changes) and opens the insurer `claim`. Corrections are credit notes.
- **Stock.** Quantities are sums of `stock_movement` rows; `dispense_fefo()` takes the earliest
  expiry first and refuses if short.
- **Audit.** Every insert, update and delete on business tables writes `audit_event`
  (partitioned by month). Reads of a patient file and break-glass access are logged by the app
  through `log_access()`.
- **Offline later.** All tables already carry `id` (UUID made on the device), `device_id`,
  `received_at`, `version`; human numbers are assigned here. That is the shape PowerSync needs;
  add a publication and sync rules per role when phase 1 reaches the offline gate.

## Compliance note (Law 058/2021)

Supabase hosts the database outside Rwanda. Article 50 requires authorisation from the NCSA to
store personal data abroad. The clinic has chosen to proceed with Supabase; record the
authorisation (or the decision to move the same schema onto the in-clinic hub, which is plain
PostgreSQL) in `setting` → `compliance` before real patient data is entered.
